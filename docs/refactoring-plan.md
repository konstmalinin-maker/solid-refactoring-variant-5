# План рефакторинга — вариант №5

Исходник в PDF отсутствует: legacy/bad_code.py — подготовленный учебный пример
по описанию DocumentManager (CRUD, версии, экспорт). Его объём не выдаётся за
упомянутые в описании 2000 строк. Baseline фиксируется до изменения дизайна.

| Принцип | Нарушение | Изменение |
|---|---|---|
| SRP | DocumentManager хранит, валидирует, экспортирует и пишет аудит | Разделить команды, запросы, версии, экспорт, валидацию и I/O |
| OCP | export меняется при каждом новом формате | Strategy + реестр экспортёров |
| LSP | ScannedDocument наследует get_text, но бросает NotImplementedError | Общий контракт данных и отдельная возможность чтения текста |
| ISP | ReadOnlyDocumentView вынужден объявлять запись и экспорт | Узкие Reader/Writer/VersionReader/Exporter/Audit порты |
| DIP | Конкретные файлы и лог создаются в бизнес-классе | Constructor injection и composition root |

## Последовательность

1. Сохранить legacy и сырые метрики Radon.
2. Зафиксировать tests_before и conftest.py. Их содержимое после этого не менять.
3. Feature-ветка: пять рабочих коммитов S → O → L → I → D. После каждого — те же тесты.
4. Добавить тесты нового дизайна, Factory Method/Builder/контейнер и точные примеры заказов A–C.
5. Измерить весь src, сравнить альтернативный функциональный дизайн, выполнить timeit.
6. Провести реальный mutmut, усилить содержательные проверки при необходимости.
7. CI: исходные и новые тесты, coverage >=85%, average CC <=10, weighted MI >=60 и каждый файл имеет реальный ранг A (MI >19).
8. PR с Issues, самопроверкой, результатами и отчётом. Внешнего участника нет — чужое ревью не имитировать.

## Сохраняемый контракт

Title strip, пустой content разрешён, ID возрастают, update без новых полей создаёт
версию, delete сохраняет историю, restore создаёт новую версию. Экспорт скана в TXT/HTML
по-прежнему возвращает NotImplementedError на границе совместимости; сам тип скана
после LSP больше не обещает интерфейс чтения текста. JSON экспортирует оба вида.

Radon маркирует MI 43.81 как A: его реальная граница A — выше 19, а не 60.
Поэтому общий численный порог PDF проверяется по взвешенному MI >=60, а каждый файл дополнительно должен иметь реальный ранг A (MI >19). Это не требует искусственно дробить уже простые модули ради MI.
Нельзя подменять фактический ранг обозначением из примерной таблицы PDF.
